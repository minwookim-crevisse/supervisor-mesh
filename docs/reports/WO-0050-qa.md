## 5. Findings

**Product (mesh), for the backend:**
1. **F-render (D125):** a slash command's text reaches the lead's input box only after Claude Code 2.1.332 renders the slash menu.
   - In the reproduction, `/context` was held from 2.0 s; `hello` was held from 0.1 s.
   - In J1 attempt 2 it took more than the 3 s default, so `pane_command` aborted at the last step.
   - Not a WO-0049 regression: `holds()`, `prompt_text()` and `_box_span` are byte-identical to `ba34a09` and give identical results on every capture.
   - The code is `mesh/pane.py` `_rendered` with the default `pane_render_wait_s = 3`, now raised to 15 by the PM-ordered rework (unverified here).
2. **F-hook:** mesh writes the `UserPromptSubmit` hook with `timeout: 10` (`mesh/init.py:417`). The hook ran 10 667 ms, and Claude Code cancelled it. No operator event and no `hook_error` were written, and nothing told the operator or the PM.
3. **F-caller:** `caller_not_pm` drops the reason. `mesh/pane.py:144` writes a fixed detail with `rule: null`, although `Resolved.reason` and `Caller.unknown(why)` exist.
   - The J2 refusal took about 24 s, against about 4 s for a good call.
   - The likely cause is a projmux timeout (`TIMEOUT_S = 15.0`, `mesh/projmux.py:34`) under a host load average of 25-35 → caller UNKNOWN. This is not proven, because nothing records it.
   - Not a regression: `identity.py`, `projmux.py` and `mcp_server.py` are unchanged from `ba34a09`.
4. **Timeouts:** mesh's projmux calls (15 s) and the hook (10 s) both sit near their limits on a loaded host, and both fail closed silently.
