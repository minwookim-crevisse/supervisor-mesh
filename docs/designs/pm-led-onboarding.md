## Problem Statement
Walking the fresh-project flow (open a projmux pane → install the plugin → `/supervisor-mesh:init` → fill Part B → `spawn-roles` → `dispatch` → lead + worker → integration gate → ship) exposed three gaps:
1. `init` scaffolds no tracker or work-orders folder, although the method says "no tracker row = no dispatch". Every project has to invent its own.
2. No skill turns the operator's own projmux pane into the Tier-0 PM. `agents/pm-orchestrator.md` is never loaded into that session, so the PM rules (never implement, single writer of coordination docs, work-order format) are not applied.
3. Prerequisites are not checked up front. `spawn-roles` and `dispatch` fail late when Claude runs outside a managed projmux pane, and `init` fails mid-run without python3 ≥ 3.10.

## What Makes This Cool
One conversation in a fresh projmux pane ends with a working mesh. The operator makes the pane the PM, the PM interviews them, and the PM builds the mesh itself. Onboarding is not a slide about the method. It is the method's first work order (row 0001), gated by evidence like every later order.

## Constraints
- Stdlib-only Python (no pip dependencies), same as `scaffold.py` and `slack_bridge.py`.
- projmux is the transport. Agents are created with `projmux create agent` and messaged with `projmux agent message send` from a managed pane.
- Never overwrite existing content. The only allowed change to an existing file is an additive, marker-guarded append. `scaffold.py` already does this for `AGENTS.md`, `.gitignore`, `package.json` and `pyproject.toml`, and `mesh init` does it once more to append a missing `WO-0001` row to an existing `docs/tracker.md`. Everything stays idempotent.
- The shipped layer stays project-agnostic (no project names, ids, or secrets).
- `init` and `spawn-roles` are `disable-model-invocation: true`: the model cannot invoke them as skills.
- The repo's own gates must stay green: `make check` (validate `--strict`, unit tests, GC, scrub).

## Premises (agreed; #2 revised after the second opinion)
1. **One entry point.** The operator's projmux pane is the PM, and one user-invoked skill, `/supervisor-mesh:pm`, makes it so. From there the PM drives onboarding.
2. **(revised) One implementation.** Preflight, init (including the tracker) and spawn live in ONE stdlib Python CLI, `mesh`. `/pm`, `/init`, `/spawn-roles` and `/dispatch` are thin wrappers that call it. The original "PM drives projmux directly" was rejected because it would duplicate the prose procedure in `skills/spawn-roles/SKILL.md`, and the two copies would drift.
3. **Preflight is a hard gate that runs first**: projmux available, Claude inside a managed projmux pane, python3 ≥ 3.10. Any failure stops with the exact fix command. The same check runs in init, spawn and dispatch.
4. **The tracker is part of the Knowledge pillar.** init lays down `docs/tracker.md` (format plus the single-owner rule) and `docs/work-orders/`. dispatch refuses an order that has no tracker row id.
5. **PM rules are enforced by instructions in v0.2.** A technical block (a PreToolUse hook on PM edits outside coordination docs) is deferred and will be measured first.
6. **(added) Onboarding is tracker row 0001.** Its DoD is captured evidence (preflight output, scaffold log, Part B answers, the role → agent UID map with `ROLE LOADED`), so `/pm` can resume from the first DoD item that isn't green.

## Approaches Considered
### Approach A: Minimal patches (rejected)
Tracker in init, a prose `/pm` skill, and a prose preflight per skill. Rejected because it contradicts revised premise 2 (duplicated procedure) and resuming depends on the model's memory.
### Approach B: `mesh` CLI as the single implementation (chosen)
See Recommended Approach.
### Approach C: projmux-hook bootstrap (deferred)
Auto-bootstrap panes through projmux lifecycle hooks. Deferred: high coupling to projmux internals, and it still needs B underneath. It could sit on top of B later.

## Recommended Approach
**B: `mesh`, one stdlib Python CLI shipped in the plugin**, with the skills and the PM as thin callers. The sub-specs below are binding for the work orders.

### 1. Launcher and Python check (R1-1)
`bin/mesh` is a POSIX `sh` shim, not Python. It runs first:
- `command -v python3` fails → print `FAIL python3 not found — install: <per-OS command from README>` and exit 3.
- `python3 -c 'import sys; sys.exit(sys.version_info < (3,10))'` fails → print `FAIL python3 <version> < 3.10 — upgrade: <per-OS command>` and exit 3.
- Otherwise it runs `exec python3 "$(dirname "$0")/../mesh/cli.py" "$@"`.

No Python code runs on an unsupported interpreter, so the python check can never crash before it prints its line.

### 2. Caller identity (R1-2)
Verified on projmux 0.17.0 (2026-10-14): a Claude session started by projmux inherits `PMX_INTERNAL_ACTIVATION_PANE_UID`. Resolving it via `projmux get panes -A -o json` gave a non-empty `status.activation.agentUID`, and that agent showed `status.phase: Running` in `projmux get agents -A -o json`. The pane's `metadata.ownerRef` is the agent; the window comes from the agent's own `metadata.ownerRef` (kind `Window`). WO-0014 re-captures this, and also captures the FAIL for Claude started by hand in a plain shell pane. `mesh` resolves the caller like this:
- read that pane uid;
- run `projmux get panes -A -o json` and take the item whose `metadata.uid` matches;
- read its `status.activation.agentUID` (the caller's agent) and owning window.

Failure handling:
- Variable absent, or no match → preflight `FAIL not inside a managed projmux pane — open the project with projmux and start Claude there`, exit 3.
- More than one match → FAIL "ambiguous pane identity", with the uids listed (exit 3).
- A matched pane whose `status.activation.agentUID` or owning window is empty (for example, Claude started by hand in a plain shell pane) → FAIL `this pane is not a managed agent — start Claude from projmux (projmux create claude, or the projmux UI) and run /supervisor-mesh:pm there` (exit 3). No fallback guessing.
- The resolved agent must appear in `projmux get agents -A -o json` with `status.phase == "Running"`; otherwise FAIL with its phase (exit 3).

Risk: the variable is projmux-internal. `mesh/identity.py` isolates this lookup in one function with a unit test, so a projmux change breaks one place loudly.

### 3. Tracker grammar (R1-4)
`docs/tracker.md` holds a Markdown table with the header `| id | title | role | depends | status | report |`, and the parser accepts nothing else.
- `id` matches `WO-\d{4}`; row 0001 is `WO-0001`.
- `status` is one of `open` · `dispatched` · `pass` · `fail` · `closed` · `n/a`.
- Row 0001's DoD lives in `docs/work-orders/WO-0001.md` as a checklist. Each item is a line `- [ ] <key>: <description> — evidence: <repo-relative path>`, where `[x]` means verified, and `<key>` is one of `preflight` · `scaffold` · `partb` · `roles` · `spawn`.
- Parsing ignores whitespace, extra columns to the right, and blank lines. Any other deviation means the tracker is unparseable: `mesh status` exits 4 and names the bad line.
- `mesh dispatch --row <id>` accepts a row only if it exists AND its status is `open` or `dispatched`. Otherwise it refuses with exit 5 and the reason.

### 3b. Role list grammar (R2-2)
In `AGENTS.md`, the section `## Roles in this project` holds one role per line: `- <role>: <description>`, where `<role>` matches `[a-z][a-z0-9-]*`.
- A line whose role contains `<` or `>` is a placeholder and does not count.
- The list is valid when it has ≥ 1 non-placeholder role and no duplicates.

The parser lives in `mesh/manifest.py` (see WO-0009) and is the only reader. `mesh status` and `mesh spawn` both take the roles from it, so "the roles from AGENTS.md" means exactly this list.

### 4. `mesh status` (R1-3, R1-7)
`mesh status` is the machine verifier for row 0001; the PM never closes the row by its own say-so. It prints JSON `{state, items:[{key, ok, evidence, reason}]}` and an exit code:

| state | when | exit |
|---|---|---|
| `uninitialised` | no `docs/tracker.md` | 10 |
| `in_progress` | some items not ok | 11 |
| `complete` | all items ok | 0 |
| `unparseable` | see §3 | 4 |
| `no_bootstrap_row` | tracker exists but there is no `WO-0001` row | 12 |
| `not_applicable` | `WO-0001` status is `n/a` (pre-0.2 project, §7) | 0 |
| `closed` | `WO-0001` status is `closed` | 0 |

Each item is checked from evidence, not from the `[x]` mark:
- `preflight`: re-run preflight live.
- `scaffold`: all pillar files exist.
- `partb`: `docs/harness/part-b-checklist.md` has no unchecked line, and `AGENTS.md` has no `<...>` placeholder in its Roles and Anchor sections.
- `roles`: the role list exists in `AGENTS.md`.
- `spawn`: every listed role has a live agent with `ROLE LOADED` in its transcript.

`mesh status --close` sets `WO-0001` to `closed` only when the state is `complete`. In every other state it refuses with exit 13, so `n/a` never becomes `closed`. For `not_applicable` and `closed`, `WO-0001.md` is not required.

### 5. `/supervisor-mesh:pm` flow (R1-5, R1-8, R1-6, R1-7)
1. `mesh preflight` (stop on FAIL).
2. **Load the PM role.** The skill body tells the session to Read the role file and adopt it. A project file `.claude/agents/pm-orchestrator.md` wins over `${CLAUDE_PLUGIN_ROOT}/agents/pm-orchestrator.md`. The session prints `ROLE LOADED pm-orchestrator` (observable). In a new session, `/pm` repeats this step; role state is never assumed.
3. `mesh status`:
   - exit 10 → `mesh init` (this creates `WO-0001` and its DoD file), then status again;
   - exit 12 → `mesh init` adds the missing row, then status again;
   - exit 4 → stop and show the bad line;
   - state `closed` or `not_applicable` → report "mesh already bootstrapped" with the status JSON, and change nothing;
   - exit 11 → continue to step 4.
4. Interview the operator for EVERY not-ok interviewable item, in checklist order (`partb`, then `roles`), before anything is spawned:
   - ask, then write the answers into the files init scaffolded; answers are never held anywhere else;
   - "I don't know" leaves the `<...>` blank and that item not ok.
5. Run `mesh spawn <roles from §3b>` only if `roles` is ok. Otherwise stop, report which items still need answers, and leave `WO-0001` open; the next `/pm` resumes here.
6. `mesh status --close`.

**Bounded exception (R1-7):** while `WO-0001` is open or absent, the PM may run `mesh init` and `mesh spawn`, and may write `AGENTS.md` and `docs/harness/part-b-checklist.md`, and nothing else. Once `WO-0001` is closed, the normal PM rule applies (never implement).

**Permission boundary (R1-6):** model-driven init/spawn is now intended, but only through the user-invoked `/pm`.
- The `/init` and `/spawn-roles` skills keep `disable-model-invocation: true` as manual entry points.
- `/pm` pre-approves only `Bash(mesh preflight:*)` and `Bash(mesh status:*)`.
- `mesh init` and `mesh spawn` go through the host's normal permission prompt, so the operator confirms the two writes that change the project.

### 6. `mesh spawn` (R1-9, R1-10)
Inputs are the roles. The role file is the project's `.claude/agents/role-lead-<role>.md` if present, else the plugin's. For each role:

| existing agent (label `role=<role>` + same cwd) | action |
|---|---|
| none | create it (caller's window, `--placement right`), then wait for `ROLE LOADED` |
| `Running` and loaded | skip |
| `Running`, not loaded within 120 s (`--timeout`) | report `loaded:false` and leave the pane (the operator may be at a trust prompt); a rerun re-checks it instead of skipping |
| any other phase (Offline / Failed / stopped) | report `stale` with the fix command `projmux delete agent uid:<uid> --socket projmux --yes`; recreate only with `--replace-stale` |

After creating panes, it applies an even-horizontal layout to the window.

Output: JSON `{role:{uid, state:created|skipped|stale|not_loaded, loaded:bool}}`. The exit code is 0 if every role is loaded, 2 if any is stale or not loaded.

### 7. Upgrade from 0.1.x (R1-12)
On a repo whose `docs/tracker.md` exists but has no `WO-0001` row, `mesh init` appends exactly one row, marker-guarded and idempotent. The row is `n/a` when `AGENTS.md` has no placeholders, which is an established project: onboarding is NOT started, and no `WO-0001.md` is written. Otherwise the row is `open`, with `WO-0001.md` written. That append is init's only edit to an existing file.

On a repo without `docs/tracker.md`, `mesh init` adds the tracker and work-orders, plus `WO-0001` with status `n/a` when `AGENTS.md` already exists without placeholders (a pre-0.2 project). Existing files are never touched.

`mesh dispatch` without a tracker exits 5 with: "this project has no tracker — run `/supervisor-mesh:init` (adds `docs/tracker.md`, changes nothing else)". The 0.2.0 release notes state this.

### 8. Manual entry points
`/init`, `/spawn-roles` and `/dispatch` call `mesh init`, `mesh spawn` and `mesh dispatch` with the same flags `/pm` uses, so the two paths share one implementation.

## Success Criteria
- In a fresh repo, with Claude started as a projmux-managed agent (`projmux create claude` or the projmux UI): install, then `/supervisor-mesh:pm`, then answer the interview. The run ends with the mesh map, every role `ROLE LOADED`, and row 0001 closed with evidence. Proven by a live QA run with captures.
- Re-running `/pm`:
  - **when `WO-0001` is closed**, changes nothing: byte-identical file hashes and an unchanged agent list;
  - **after a partial run**, only `docs/tracker.md`, `docs/work-orders/WO-0001.md` and the Part B files may change. No scaffolded file or agent is created twice (unchanged hashes for every other file; the agent count grows only by roles not yet created).
- Outside a managed pane, or with python3 < 3.10: `/pm`, `/init`, `/spawn-roles` and `/dispatch` stop at preflight with the fix command, before any write.
- `mesh dispatch` without a tracker row id is refused.
- The manual `/spawn-roles` path and the `/pm` path issue identical `projmux create agent` arguments. This is guaranteed because both call `mesh spawn`, and checked by a unit test with a fake projmux.
- `make check` stays green; there is a new regression test file for `mesh`, and scrub reports 0.

### Expanded scope items
- **E1 `.mesh/` layout.** `mesh init` creates `.mesh/state.json` (empty work set), `.mesh/config.toml` (Vault path, project folder, retry limits, verification commands, Slack enabled flag) and the generated `docs/tracker.md` view. Re-runs never overwrite user values; missing / conflicting / unset keys are reported separately.
- **E1b Standard minimum layout (what `mesh init` builds; this repo dogfoods it, DEC-0014).**

  | path | pillar / purpose | writer |
  |---|---|---|
  | `AGENTS.md` | instruction entry + layer map | orchestrator |
  | `.mesh/config.toml` | Vault path, project folder, retry limits, verification commands, Slack flag | orchestrator via `mesh` |
  | `.mesh/state.json` | work items, attempts, transitions, evidence (source of truth, DEC-0010) | `mesh` only |
  | `docs/tracker.md` | generated read-only view of `state.json` | `mesh` only |
  | `docs/work-orders/` | dispatch orders (one file per batch) | orchestrator |
  | `docs/reports/` | lead reports and QA evidence, `WO-<id>-<role>.md` (each lead writes its own file only) | leads |
  | `docs/designs/` | design docs and their review records | orchestrator |
  | `docs/decisions/` | decision log, outranks every other doc | orchestrator |
  | `docs/conventions/` | glossary + constraint rationale | orchestrator |
  | `docs/harness/part-b-checklist.md` | Part B facts to fill | orchestrator |
  | `tests/`, `scripts/audit.sh`, `scripts/gc/`, `.github/workflows/housekeeping.yml` | feedback loop + GC | qa |
  | stack constraint config (`.dependency-cruiser.cjs` / `.eslintrc.cjs`, or `.importlinter` + pyproject ruff/mypy) | constraint pillar | qa |

  No other top-level docs folder is created; QA evidence lives in `docs/reports/` (no separate `docs/qa/`). The `templates/AGENTS.md` layer map, `templates/part-b-checklist.md` and `mesh/docs.py` manifest list exactly this table (WO-0010). `scripts/gc/check_docs_drift.py` is extended to fail when a path in the AGENTS.md layer map is missing.
- **E2 State machine (stdlib, behind an interface).** States `draft → ready → running → verifying → verified`, plus `rework`, `blocked`, `cancelled`. Every transition is a `mesh work <verb>` command with guards:
  - `ready` needs a contract (goal, done criteria, role, depends, scope);
  - `running` needs depends verified, the target agent live (label + cwd + Running), and a new attempt id;
  - `verifying` needs the attempt id and the changed commit;
  - `verified` needs every required verification command recorded with exit code, timestamp and the same commit; a later commit invalidates the evidence;
  - `rework` needs a failure record (class + evidence);
  - retries beyond the configured limit force `blocked`.
  Stale or duplicate results (older attempt id) are rejected. State writes use a lock file plus atomic replace. Replaces eng-review D8; D7's parser only imports an existing Markdown tracker once.
- **E3 Slack is a required init step (D02).** `mesh init` asks for Slack setup and records `slack.enabled`; preflight reports Slack unconfigured as a FAIL with the fix, unless the operator explicitly opts out (recorded as a decision).
- **E4 Slack ↔ work linkage.** A top-level request creates a `draft` work item and maps `channel:thread_ts → work id`. Replies in that thread attach to that item; the PM posts progress and results in the same thread. An item awaiting operator input is in `blocked(reason=awaiting_user)` and resumes when a thread reply arrives. Duplicate Slack deliveries are deduplicated by message ts.
- **E5 Role profiles.** Each role maps to a projmux profile (model, effort, instructions); `mesh spawn` passes `--profile`. Every rule is reported as enforced (projmux / tool permission) or prompt-only; prompt-only rules are never shown as enforced.
- **E6 Evidence-gated completion.** `mesh work verify` runs the configured verification commands itself and records the outputs; a lead's prose report alone cannot reach `verified`. Missing tools are recorded as `not_run` (not as pass).
- **E7 Vault records (DEC-0011).** After a gate passes, `mesh` writes session / failure / decision records to `<vault>/<project>/` using the bundle's templates, checking the target hash first. It never writes outside the project folder; common knowledge is promoted by a human.
- **E8 Slack hardening carried in.** N-01: `send` only accepts files under `scripts/slack/outbox/`.
