| D121 (WO-0023 delta, N1; revised after security review) | D113 code secrecy and threat model | mesh generates the code and keeps only its hash; the plaintext travels to the popup only through a one-shot FIFO (in a fresh 0700 dir mesh created; written once, never a regular file; a reader that steals it leaves the popup without a code, a visible failure); the operator's typed text comes back as RAW text through a second FIFO and mesh compares its hash with the stored one (never a hash or flag computed by the popup); exactly one answer while the popup pid lives; a pre-existing FIFO/file or a second writer is refused; the dir is removed at once. | D123 (WO-0024 live F10) | when the transcript proof runs | live on Claude Code 2.1.327 the user entry reaches the transcript only after `UserPromptSubmit` returns, so the D110 proof cannot run inside the hook. At citation, the latest real user prompt is found by a positive structural rule: a `type=user` entry, not `isMeta`, `origin.kind == "human"`, text content, not sidechain (peer deliveries, task notifications, tool results and system lines are skipped; a missing field fails closed); the entry's timestamp must be at least the candidate's record time minus 5 s; only the newest candidate of that session may bind the latest entry; exactly one usable event per transcript entry. | D124 (WO-0023 final gate, F13) | judging a confirmation | mesh judges only after the `display-popup -E` it started has returned; it refuses when more than one helper process ever opened either FIFO, and when the popup's helper reports `no code` (a third outcome on the answer FIFO, or its exit status). A stolen code is therefore always a refusal the operator can see, never an approval behind a refusal screen. Refusal reasons: `second_writer`, `no_code`, `no_answer`, plus the D122 helper-failure codes; approvals take about 1.5 s longer |
| D125 (WO-0024 step f, live) | pane_command render wait | live on Claude Code 2.1.328 a typed `/command` reaches the input box only after the slash menu renders (absent at 0.5 s, present at 1.5 s), so the immediate capture after `send-keys -l` aborted with `aborted_text_not_on_prompt`. | D126 (DEC-0016, WO-0038 F1; amends D102 (a)) | dispatch header and workers | the header `work_dispatch` prepends tells the lead that each worker is its in-process subagent (brief, receive directly, verify, rework); only an order that explicitly asks for a separate worker agent uses the D102 path (label `worker-of=<role>`, `<WO>-done` message, `projmux agent wait`). ## Shape

- One package `mesh/` at the plugin root. Every behaviour lives in plain functions; two thin front doors call the same functions:
  - `mesh/cli.py` (CLI, also used by hooks: `mesh event record`);
  - `mesh/mcp_server.py` (stdio MCP server: `initialize`, `tools/list`, `tools/call`; newline-delimited JSON-RPC; logs to stderr only).
- `.mcp.json`: server `supervisor-mesh`, command `python3`, args `${CLAUDE_PLUGIN_ROOT}/mesh/mcp_server.py`. The project root is the server's working directory (`CLAUDE_PROJECT_DIR` when set).
- State: `<project>/.mesh/state.json` is the source of truth (lock file + atomic replace + compare-and-set, section 8 of the state model). `docs/tracker.md` becomes a generated view; an existing tracker is imported once as legacy rows (normalized, never deleted).
- Caller identity: the projmux pane of the calling session (role label `pm` or the lead's role), isolated in `mesh/identity.py`; unknown pane = refused for every verb except read-only tools. `operator` is never inferred: `override` requires a hook-recorded operator event (section 9a).
- The transition table is one declarative structure in `mesh/state.py`; the MCP tool, the CLI and the tests read it. Unlisted verb x caller x state = refused and recorded.

## MVP tools

| tool | caller | does |
|---|---|---|
| `mesh_init` | pm | scaffold the 4 pillars (wraps `skills/init/scaffold.py`); `dry_run` and `apply` are separate calls; creates `.mesh/` and imports a legacy tracker |
| `mesh_status` | any | items by state, live leads (projmux), pending actions; read-only |
| `work_list` / `work_show` | any | read items / one item record; read-only |
| `work_new` | pm | `new`: draft with goal, done criteria, role, type, depends |
| `work_transition` | per table | every other verb of section 4 (`ready`, `start`, `submit`, `verify`, `fail`, `reassign`, `split`, `unblock`, `reject`, `ack`, `close`, `cancel`, `revise`, `reply`, `override`); args validated per verb |
| `work_dispatch` | pm | `dispatch`: sends the work order to the role lead with `projmux agent message send` (standard header: read set, mission, operating model, 4 principles, evidence-first DoD, constraints, report target); records the message-ref |
| `companions_install` | pm | run the D88 install plan for the missing companions after operator approval; returns each command's exit code; never touches user scope |
| `mesh_metrics` | any | D90 counters; read-only |
| `tracker_render` | pm | regenerate `docs/tracker.md` from state.json |
| `pane_command` | pm | type one slash command (and its args) into a lead's pane (D84). Guards: the target is a live agent of THIS project (projmux uid, cwd under the project root), never the PM's own pane; the text starts with `/` and is one line (no newline, no control characters); the call cites a hook-recorded operator event id (section 9a of the state model) that is fresh, single use and names the command (D85); receipts are a separate event type and never count as operator events; the pane shows an idle prompt before typing; the command is typed literally (`send-keys -l`) then Enter; the receipt (target uid, command, event id, time) is appended to the item history and `.mesh/events.jsonl`, and the target lead is messaged that the keypress was operator-instructed. Never answers trust or permission prompts. |

`verify` runs the item's verification commands (`.mesh/config.toml`, `tomllib`) in a disposable `git worktree` at the submitted commit, argv only, with a timeout; exit codes and timestamps are bound to commit + contract version + config hash. A prose report never reaches `verified`.

## Out of the MVP (recorded, not built)
Slack watcher verbs (`draft`, `attach` from Slack; the slack-setup skill keeps working as is), `mesh_feedback` / `mesh_fleet_status` (D103, 0.3.0), init installing the lint devDependencies its npm scripts need (pilot finding: eslint/ts-prune missing), audit template 'zero checked = FAIL' rule (pilot finding), reply-expectation flags on dispatch (pilot finding E), enforced scope serialization (D94 stage 2), `revalidate` at an integration gate, metrics beyond the D90 counters (baseline comparison report, D43/D50), LangGraph (stage 2).

## Acceptance (evidence-first)
1. Unit tests: table walk (invariants 1-4), one test per invariant 5-15 where expressible, CAS stale write refused, lock contention, legacy tracker import, identity refusal, MCP handshake + `tools/list` + one `tools/call` per tool over a real stdio pipe.
2. The TLA+ model (WO-0020) and `mesh/state.py` agree: a conformance test replays the model's table rows against `state.py`.
3. `make check` exit 0, scrub 0, `claude plugin validate . --strict` exit 0.
4. Live: in a throwaway projmux project, install the plugin at project scope, `/mcp` lists `supervisor-mesh` connected, the PM pane runs `mesh_init` (dry run, then apply), `work_new` -> `ready` -> `work_dispatch` to a spawned lead, the lead `start`/`submit`, `verify` passes, PM `close`; file hashes and state.json captured as evidence.
